# NovaSupport AI

A GenAI customer-support automation platform for **NovaCart Technologies**, a **fictional** e-commerce company.
An AI agent answers customers using retrieved company policy (RAG) and controlled, authorised tools, verifies its answers before sending them,
asks for confirmation before risky actions, routes high-risk ones to a human approval queue, and escalates to human agents with full context.

> **All company data is synthetic.** NovaCart, its customers, orders, payments, refunds, shipments, tickets, employees and policy documents are fictional,
> generated by `backend/app/services/synthetic.py` and `data/knowledge_base/*.md` solely for demonstration and testing. No real or confidential data is used.
> There are no production users; every number below comes from synthetic data and a synthetic test set.

## Problem
Support teams spend most of their time on repetitive, policy-bound questions (where is my order, am I eligible to return this, how long does a refund take).
A naive chatbot invents policies, leaks other customers' data, or performs actions it should not. This project explores the engineering around the model:
grounding, authorisation, verification, human-in-the-loop and measurement.

## Features
* Chat with citations, visible action steps ("Order database checked", "Shipment status retrieved"), confirmation dialogs and escalation notices (no chain-of-thought is exposed).
* **RAG**: parser → cleaning → section-aware chunking → metadata → embeddings → pgvector (HNSW) → hybrid retrieval → rerank → numbered context; citations are generated only from chunks actually used.
* **19 intents** with structured output, **sentiment/urgency** analysis, memory in **Redis** (30-minute TTL, redacted).
* **16 controlled tools** with parameter validation, ownership checks, risk levels (LOW/MEDIUM/HIGH) and a `needs_confirmation → pending_approval → executed` flow.
* **Human-in-the-loop**: admin Approvals screen; approving executes the tool, rejecting changes nothing.
* **Guardrails**: prompt-injection and third-party-PII detection, credential redaction, PII masking, tool authorisation, "not enough verified information" fallback.
* **Response verifier**: groundedness, citation validity, policy compliance, unsupported claims, sensitive data; failed answers are regenerated or escalated.
* **Escalation tickets** carry customer, conversation summary, intent, sentiment, urgency, order, policy sources and an AI recommendation.
* **Admin dashboard** (conversations, AI resolution/escalation rates, latency, tickets, tool failure rate, retrieval quality, groundedness, citation accuracy, estimated LLM cost, charts), conversations, tickets, approvals, customers (masked), AI evaluation, knowledge base, system health.
* **Observability**: structured JSON logs with request/conversation ids, Prometheus metrics (LLM, tools, RAG, DB, HTTP, escalations, guardrails, verifier), a provisioned Grafana dashboard, optional OpenTelemetry tracing.
* **Evaluation**: 126 synthetic cases and a runner that computes every metric from actual runs.
* **Free / local-first**: default mode needs no LLM, no paid API, no model download. Ollama and OpenAI-compatible endpoints are optional.

## Architecture
See `docs/architecture.md`. In short: React → FastAPI → Orchestrator → (RAG | Tools | Verifier | Escalation/Approvals) → PostgreSQL/pgvector, Redis; Prometheus/Grafana alongside.

## Database setup and knowledge-base ingestion
Automatic on startup. To redo manually:
```bash
docker compose exec backend python scripts/seed_database.py          # drops and re-creates the synthetic data
docker compose exec backend python scripts/ingest_knowledge_base.py  # re-chunks, re-embeds, re-indexes
python scripts/generate_data.py                                      # writes data/synthetic/*.json (already included)
```
There is no Alembic migration history: schema is created with `create_all` plus idempotent pgvector DDL in `backend/app/database/session.py`. Add Alembic if you evolve the schema.

## What was and was not verified when this was built
* **Verified by running:** the 73 pytest tests (SQLite); seeding, pgvector ingestion (HNSW index, `<=>` queries), retrieval, chat API, Redis memory and the full evaluation on a **native PostgreSQL 16 + pgvector + Redis** install; the frontend type-checks and builds with Vite.
* **Not run in the build environment:** `docker compose up` itself (no Docker daemon was available), so the Dockerfiles, nginx proxy config, compose wiring, Prometheus scraping and the Grafana dashboard were only syntax-checked. Expect to fix small issues on first run.
* **Not verified:** the React UI was compiled but not inspected in a browser or on mobile; Ollama / OpenAI-compatible modes and `sentence-transformers` embeddings were exercised only through fallback paths (the code degrades to the extractive answer when the LLM is unreachable); OpenTelemetry tracing was not exercised.

## Limitations and future improvements
* Intent classification, injection detection and the verifier are rule/lexical based: good for a transparent demo, brittle on novel phrasing. Next steps: a small fine-tuned classifier, an LLM-as-judge verifier, a held-out evaluation set.
* Default hash embeddings are lexical-ish; use `EMBEDDING_BACKEND=sentence-transformers` for semantic retrieval.
* Demo-mode answers are extractive and read stiffly; enable a local LLM for natural language (the verifier still gates it).
* Add Alembic migrations, real auth (SSO, rate limits, refresh tokens), background workers for approvals/notifications, multilingual support, a feedback loop from agents.
